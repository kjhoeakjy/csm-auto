## 1. 실행 구조
```
scheduler.py (APScheduler)
  ├ live   : 매 분기 첫 달 15일 02:00 직전 분기 처리 (CronTrigger, 등록 시연)
  └ replay : 가상 시계로 2015Q4~2018Q4 순차 처리 (무인 배치)
        ↓ 같은 함수
pipeline.run_quarter(T)
  as-of 자르기 → 선행 점검 → 조기 결과 점검 → 후행 검증 → 판정(rules.py)
  → [조치 검토일 때만] 개선 후보 10종 모의 배포 검증(candidates.py)
  → 권고 + 근거 3개 → decision.json · candidates.csv/joblib · run_log.jsonl
        ↓
report.build → report.verify (숫자·분기 자동 대조, 실패 시 발행 보류)
llm_report (선택): 도구 5개로 조회 → 초안 → 같은 대조 + 판정 일치·원인 단정·코드명 검사
m08_build_app → app/index.html (상태 1개 + 권고 1줄 + 근거 3개, 상세는 접힘)
```

## 2. 재현성·버전
- 모든 결과에 `input_key` = 분기 | 데이터 ID(원천 SHA1@스냅샷) | 모형 ID | 규칙 버전 | 코드 해시
- 같은 input_key로 이미 성공한 분기는 다시 만들지 않음 (재실행 중복 방지 시험 통과)
- **규칙 버전별 결과 폴더 분리** `runs/r1`, `runs/r2`, `runs/r2.1`. 시뮬레이션 결과는 `decision_<주입명>.json`으로 실데이터와 분리
- 난수 SEED 42, LightGBM 구조, 반복 수 고정

## 3. 실패 처리 시험 (시뮬레이션, `results/m07_robustness.csv`)
| 시험 | 기대 | 결과 |

| 결과 코호트 1%만 도착 | 판정 유보 | 통과 (r2.1 보완 후. r2에서는 예외로 '실패' 기록) |

## 5. LLM 보고서 (시험 (Claude Haiku 5.5))
- **역할** 검증된 도구 5개(판정, 결과 점검, 입력 점검, 후보 결과, 방법 노트)로 조회, 담당자용 요약, 근거 3개, 조사 항목 작성
- **자동 검사** 상태, 권고가 decision.json과 같은지, 모든 숫자, 분기가 근거 JSON 또는 도구 결과에 있는지, 원인 단정 표현, 도구 이름, 영문 코드명 노출, 근거 개수
- **프롬프트 lr1 시험 2분기** 2건 모두 보류 (근거 5개, 연도 표기), lr2에서 근거 3개 고정, 외부 사실 금지, 2건 모두 발행
- **한계** 숫자 대조는 '근거에 있는 값인가'만 확인. 값이 엉뚱한 항목에 붙은 경우(예시 사유 개수를 신호 건수로 서술)는 잡지 못함, 화면 주 결과는 규칙 기반 문장, LLM 초안은 담당자 보고서 보조로만 사용
- 전체 13분기 비교와 최종 생성(Opus)은 비용 승인 후 진행
